# ADR 0001: Replace Boolean `verified` With a Verification Ladder

- Status: Accepted
- Date: 2026-09-16
- Decision owners: Theseus maintainers
- Autopsy: [`reports/audit/corpus-autopsy.md`](../../reports/audit/corpus-autopsy.md) — regenerated by `make corpus-autopsy`

## Context

Theseus grew three layers: ecosystem recipe normalization, behavioral oracles checked against installed libraries, and clean-room synthesis. PLAN.md's original success bar for Layer 3 was three isolated Python packages and one Node package. The synthesis loop then scaled that bar until `theseus_registry.json` listed on the order of 390 packages with `status: verified`.

That bit does not mean what the README claimed. The clean-room harness requires zero-argument invariant functions. The `theseus_*` factory produced three such wrappers per package, often with `expected: true`. Isolation (the original package cannot be imported) is a real and useful check. It is not regenerative qualification, it is not API parity, and it is not a drop-in replacement.

Two exhibits from the corpus:

- `zspecs/json.zspec.zsdl` calls `json.dumps` / `json.loads` with RFC-shaped vectors. That is a Layer 2 public-API oracle.
- `zspecs/theseus_json.zspec.zsdl` grades a recursive-descent codec on three wrappers (`json_loads_int`, `'a' in dumps(...)`, one round-trip). `zspecs/theseus_antigravity_cr.zspec.zsdl` grades an easter egg on three functions that return `True`.

`docs/SPECIFICATION.md` already said production replacement was out of scope. Public docs still advertised a verified rewrite ecosystem. That is a deferred claim advertised as a guarantee.

A full refresh therefore starts by classifying the corpus and withdrawing the qualification claim. Format changes and new synthesis come after this decision, not before.

## Decision

### 1. Split the product claim

Theseus has two honest products. They share oracles and provenance. They do not share a success metric.

| Product | Question | Scale |
|---|---|---|
| **A — Characterization** | Can we describe an OSS package and check that description against the installed original? | Corpus-scale |
| **B — Regenerative replacement** | Can we generate an implementation from an accepted spec, in an empty workspace, that passes a **held-out** oracle without the original in the model context or the runtime? | Gold set of tens, not hundreds |

Replacing the OSS universe (`Project C`) is rejected as a near-term goal.

### 2. Introduce a ladder. Retire the boolean as a product claim.

Every spec and every registry package sits on exactly one current rung. Higher rungs require the lower ones. Model confidence never promotes a package.

| Rung | Meaning | Who may claim it |
|---|---|---|
| `inventoried` | Recipe / identity metadata exists. No behavioral contract. | Layer 1 records, rust wrapper specs, presence-only shims |
| `characterized_draft` | A behavioral description exists (ZSDL or future Markdown). Not reviewed as sufficient. | Most Layer 2 specs that are not yet public-API oracles of useful depth |
| `characterized` | A person accepted the description, including an uncertainty ledger. | Gold-set families under `gold/<family>/` after Phase 2 ([ADR 0003](0003-characterization-loop.md)) |
| `oracle_bound` | Executable invariants call the **public API with arguments** and pass against the **installed original**. | Layer 2 `python_module` / `node` / `ctypes` / `cli` specs of moderate or deep quality |
| `spec_sufficient` | An independent review says the spec could support regeneration. Held-out vectors exist and are not in the synthesizer prompt. | Future Phase 1–2 |
| `regenerated` | Empty-workspace generation passed **generated** tests. Not acceptance. | Future Phase 3 |
| `qualified` | Held-out oracle passed, isolation held, qualification protocol ran at least twice. Original source was not in the generator context. | None today (Phase 3 attempted 10 families; dual-generation did not occur — [ADR 0004](0004-qualification-protocol.md), [ADR 0005](0005-characterization-is-the-product.md)) |
| `legacy_isolation` | Historical `status=verified`: listed invariants passed with the original blocked. **Not a product rung.** Kept as evidence of the old gate. | Essentially the entire current registry |

`status: verified` in `theseus_registry.json` is hereby **isolation evidence only**. It does not mean `oracle_bound`, `spec_sufficient`, `regenerated`, or `qualified`.

### 3. Withdraw qualification

Every registry package whose `status` is `verified` is withdrawn from any replacement or qualification claim. The machine-readable list is [`reports/audit/withdrawn-verified.json`](../../reports/audit/withdrawn-verified.json). Count and reasons are regenerated by `make corpus-autopsy`.

`tools/registry.py` may keep writing `status=verified` after the old isolation harness until a later ADR changes the registry schema. Callers MUST treat that field as `legacy_isolation`. `is_allowed()` remaining true for those packages is a compatibility policy, not a qualification claim.

No package is `qualified` as of this decision.

### 4. Oracle quality and contract shape are first-class

The autopsy classifier records, per spec:

- **oracle quality:** `empty` | `presence` | `factory_shallow` | `self_test` | `wrapper` | `shallow` | `moderate` | `deep`
- **contract shape:** `public_api` | `self_test_wrapper` | `wrapper` | `presence` | `cleanroom_public_api`
- **feasibility** (replacement of the original): `high` | `medium` | `native_core` | `os_binding` | `stdlib_interpreter` | `wrapper` | `infeasible` | `needs_review`

A spec is `oracle_bound` only when the contract shape is `public_api` and quality is `moderate` or `deep`. Zero-argument wrappers that return hardcoded values cannot occupy that rung.

### 5. Gold set, not wave count

The intended regenerative gold-set **families** (Phase 3 targets, not current qualifications):

`json`, `base64`, `hashlib`, `uuid`, `semver`, `tomllib`, `tomli`, `struct`, `binascii`, `urllib_parse`, `difflib`, `pcap`/`libpcap`, `pcapng`, `fnmatch`, `shlex`, `hmac`

A family enters the working candidate list only when a **Layer 2** spec (not a `theseus_*` factory spec) is `public_api` and `moderate`/`deep`. Duplicate `_cr` / `_cr2` / `_rust` waves of the same family are inventory, not progress.

If fewer than half of an attempted gold set reach `qualified` after a held-out oracle protocol, replacement stops being the product claim. Characterization remains.

### 6. Authority versus evidence versus generation

This ADR adopts the literate-ai split as Theseus policy. Implementation of new formats is Phase 1.

- **Authority** is a reviewable characterization (today: ZSDL; next: Markdown with typed frontmatter).
- **Evidence** is compiled oracles, receipts, and isolation logs (canonical JSON).
- **Generation** is disposable. Committed `cleanroom/**` trees are historical artifacts, not behavioral authority.
- The synthesizer must not see the held-out oracle.
- Original implementation source may be inventoried as quarantined evidence for characterization. It must not enter a clean-room generation context.

ZSDL remains the executable oracle language until Phase 1 replaces or wraps it. It is not a sufficient human-authority document.

### 7. Constraint classification

| Claim | Class |
|---|---|
| Specs are derived from public documentation for generation; original source is not a generation input | **Invariant** |
| Isolation: a clean-room implementation must not import the original | **Invariant** for replacement work |
| Generated source is not behavioral authority | **Invariant** |
| `status=verified` means qualified replacement | **Rejected** |
| Zero-argument invariant wrappers | **Retired policy** for new specs; existing factory specs are `legacy_isolation` |
| Python 3.9 stdlib-only tools | **Policy/default**, not an invariant of the ladder |
| 70% test coverage, tests in `tests/` | **Repository policy** |
| Cross-ecosystem recipe schema | **Policy**; Layer 1 is inventory, not characterization |

## Consequences

Positive:

- Docs can describe Layer 2 as a real oracle corpus without laundering Layer 3 factory output as replacements.
- Phase 1 can change formats without pretending 390 packages already climbed the new ladder.
- Gold-set work has a kill gate.

Costs:

- README, AGENTS.md, architecture notes, and the registry description must stop saying “392 verified packages” as if they were replacements.
- Downstream tools that filter `--verified` still mean “legacy isolation passed.”
- Re-grading Layer 2 specs onto `characterized` (human review) is done for the intended gold-set families (`gold/<family>/uncertainty.yaml`, ADR 0003). The autopsy still marks most of the corpus `oracle_bound` mechanically.

## Rejected alternatives

**Keep `verified` and add a parallel `ladder` field later.** Rejected as the primary story. A parallel field is allowed as implementation; the *claim* is withdrawn now.

**Delete the clean-room tree.** Rejected. The implementations are historical evidence and some (for example `theseus_json`'s parser) are real code graded on a toy spec. They are not qualified.

**Treat Layer 2 json as already qualified.** Rejected. Qualification requires empty-workspace regeneration against a held-out oracle. Layer 2 only proves the oracle matches the original library.

## Follow-up

- Phase 1 — format spike on JSON: Markdown authority, public-API oracle, held-out vectors, no zero-arg wrappers. **Done** ([ADR 0002](0002-json-authority-format.md), `gold/json/`).
- Phase 2 — characterization loop with uncertainty review; deepen the best Layer 2 oracles. **Done** ([ADR 0003](0003-characterization-loop.md), `docs/characterization-loop.md`, `gold/<family>/`).
- Phase 3 — gold-set regenerative qualification.
- Phase 4 — keep or drop replacement as a product claim.
